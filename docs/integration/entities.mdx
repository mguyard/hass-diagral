## List of entities

The Diagral integration operates in Hub Mode, meaning that all configurations will be created as devices, and each device will consist of a set of entities.

| Sensor                    | Description                                                                                |
| ------------------------- | ------------------------------------------------------------------------------------------ |
| Central                   | Alarm Control Panel with 3 modes: Away, Home and Disarmed                                  |
| Anomalies                 | Sensor displaying the number of anomalies in state and details in attributes               |
| Active Groups             | Sensor displaying the number of active groups in state and details per group in attributes |
| Webhook                   | Diagnostic sensor showing whether Diagral events can reach Home Assistant                  |
| Last webhook              | Diagnostic sensor with the time of the last Diagral event received (disabled by default)   |
| Central connection        | Diagnostic binary sensor, connected while central polling succeeds through either backend |
| Cloud endpoint (ping)     | Diagnostic binary sensor, connected while the public cloud endpoint answers; this does not establish that authenticated Emerald calls work |
| Primary API Emerald       | Diagnostic binary sensor reporting the last authenticated Emerald central probe, present when the SDK supports automatic emergency mode |
| Fallback API              | Diagnostic binary sensor showing whether Topaze is serving successful central reads, present when the SDK supports automatic emergency mode |
| Active API                | Diagnostic enum showing Emerald (primary) or Topaze (fallback), unavailable if neither can return a valid central state |

<Info>
All entities are refreshed every `5 minutes` (fixed) or upon receiving a [Webhook](/integration/webhook) from the Diagral Cloud.

Central refreshes are bounded to `2.5 minutes`. With automatic emergency support, a temporary Emerald failure triggers a Topaze attempt within that budget. Older SDK versions keep the standard Emerald retries, up to twice with longer waits. The alarm panel becomes unavailable if no backend returns a valid central state, and recovers at the next successful refresh.
</Info>

## Fallback API - Details

With [automatic emergency mode](/integration/setup#automatic-emergency-mode), **Fallback API** is connected while the last central refresh succeeded through Topaze. It is disconnected when Emerald is working and the fallback is on standby, or when the fallback read failed. Its state is unknown before the first central read. The same entity stays available during outages and backend switches.

This diagnostic uses the SDK's current result and sends no additional API requests. It follows a backend change made during a command's read-only preflight as well as normal polling. It is independent of **Cloud endpoint (ping)** and does not confirm webhook delivery or the availability of detailed anomalies.

Downloaded diagnostics also report whether automatic failover is supported, which backend is active, the fallback connectivity result and whether the anomalies read succeeded. An unavailable anomaly count is exported as `null`, never as a confirmed zero.

## Primary API Emerald and Active API - Details

**Primary API Emerald** reports an authenticated configuration and status read of the central. A successful public ping cannot turn it on. **Active API** identifies the service currently providing a validated central state, so the combination explains what is happening:

| Primary API Emerald | Fallback API | Active API | Meaning |
| --- | --- | --- | --- |
| Connected | Disconnected | Emerald (primary) | Normal operation; Topaze is on standby |
| Disconnected | Connected | Topaze (fallback) | Emerald failed; emergency service is working |
| Disconnected | Disconnected | Unavailable | Neither service returned a valid central state |
| Unknown | Unknown | Unknown | No central probe has finished yet |

These entities keep the same identifiers through failure and recovery. Downloaded diagnostics include the primary probe result and its exception class, without account information or raw server error messages.

## Central - Details

Central entity is an [Alarm Control Panel](https://www.home-assistant.io/integrations/alarm_control_panel/) entity type.
This entity supports 3 modes (Away, Home and Disarmed) and 5 states:

| State | Meaning |
| --- | --- |
| `arming` | The alarm waits for a set time before activating, to let you leave or enter and type the code on the keypad |
| `armed_away` | The alarm is fully activated |
| `armed_home` | The alarm is activated in home mode |
| `disarmed` | The alarm is not activated |
| `triggered` | [An intrusion has been detected](/integration/entities#triggered-state) |

### Triggered state

The `triggered` state is not a proper alarm state but is activated when receiving an ALERT [webhook](/integration/webhook) from Diagral Cloud.
The `triggered` status is only removed when the alarm is disarmed.
When the triggered state is activated, the entity contains attributes (if available in the webhook):

```yaml
trigger:
  group_name: Motion Sensors
  group_id: 3
```

Alert codes that trigger it:

| Code | Alert |
| --- | --- |
| `1130` | INTRUSION |
| `1139` | INTRUSION-CONFIRMED |
| `1141` | PREALARM-CONFIRMED |

## Anomalies - Details

Anomalies are fetched independently after the central's configuration and status. A slow or failed anomaly request does not prevent the alarm panel from loading or receiving its status. The anomalies sensor is unavailable until its own read succeeds; a failed read never means zero faults. Subsequent successful central polls request another anomaly refresh, without overlapping a read already in progress.

Detailed anomalies continue to use Emerald in emergency mode and can remain unavailable while the central state is updating through Topaze. The Topaze `defaults` field is not interpreted as a detailed anomaly list.

If a transient webhook verification fails, the local build retains a previously owned listener only when its stored ID and exact URL hash still match. The receiver remains routable after setup and retries, but the repair stays visible until the cloud subscription can be confirmed. Listening locally does not prove that Diagral is delivering events.

<Card title="Example of Anomalies Sensor Attributes" icon="newspaper">
```yaml
unit_of_measurement: anomalies
icon: mdi:alert-box
friendly_name: Home Alarm Anomalies
created_at: 2025-02-25T17:45:10.796890+01:00
updated_at: 2025-02-25T18:14:08.936700+01:00
anomalies: # [!code highlight]
  sensors: # [!code highlight]
    - serial: '123' # [!code highlight]
      index: 0 # [!code highlight]
      group: Kitchen # [!code highlight]
      label: Kitchen Door # [!code highlight]
      anomaly_names: # [!code highlight]
        - id: 23456789 # [!code highlight]
          name: sensorAlert # [!code highlight]
        - id: 23456790 # [!code highlight]
          name: sensorAlert2 # [!code highlight]
    - anomaly_names: # [!code highlight]
        - id: 98765432 # [!code highlight]
          name: sensorAlert2 # [!code highlight]
  central: # [!code highlight]
    - anomaly_names: # [!code highlight]
        - id: 12805213 # [!code highlight]
          name: mainPowerSupplyAlert # [!code highlight]
    - serial: 234 # [!code highlight]
      group: Détecteurs de Mouvements # [!code highlight]
      anomaly_names: # [!code highlight]
        - id: 12345678 # [!code highlight]
          name: mainPowerSupplyAlert2 # [!code highlight]
fault_count: 5 # [!code highlight]
```
</Card>

The sensor state counts the devices with an anomaly. The `fault_count` attribute counts every fault across all devices, so one device with two faults contributes `1` to the state and `2` to `fault_count`. With no anomaly, `fault_count` is `0`.

All anomalies are under the `anomalies` key. The first level (`sensors` and `central` in this example) is the type of element with anomalies: `sensors`, `badges`, `sirens`, `cameras`, `commands`, `transceivers`, `transmitters` or `central`.

Each anomaly can have several attributes:

| Attribute | Description |
| --- | --- |
| `serial` | The serial number of the element that triggered the anomaly (optional) |
| `index` | The name of the element, looked up among the elements of the same type, or its number when it is not found (optional) |
| `group` | The group of the element: its name if defined, otherwise its ID (optional) |
| `label` | The name of the element that triggered the anomaly (optional) |
| `anomaly_names` | Every fault of the element, each with the `id` and `name` defined by Diagral |

Using this attribute format, you can leverage Jinja2 templates to extract and utilize the information you need.
Below is a quick and simple example for a [Home Assistant Template](https://my.home-assistant.io/redirect/developer_template/) (replace `sensor.home_anomalies` with your actual entity):

```jinja title="Template"
{% set anomalies = state_attr('sensor.home_anomalies', 'anomalies') or {} %}
{% for location, devices in anomalies.items() -%}
{% for device in devices -%}
{{ device.get('label') or device.get('index', location|capitalize) }} — {{ device.anomaly_names|map(attribute='name')|join(', ') }}
{% endfor -%}
{% endfor %}
```

<Info>
More templates, and an automation that notifies you when a new fault appears, are in [Examples - Anomalies](/integration/examples#anomalies).
</Info>

## Webhook - Details

Intrusion alerts only reach Home Assistant through the [webhook](/integration/webhook). This diagnostic sensor tells whether they can, even while Diagral cannot be polled:

| State | Meaning |
| --- | --- |
| `connected` | Events are received |
| `owned_elsewhere` | The subscription points to another installation; a repair explains how to take it over |
| `registration_failed` | Diagral or Home Assistant Cloud did not answer; it is retried every hour |
| `no_url` | Home Assistant has no external `https://` address nor Home Assistant Cloud |
| `unregistered` | You unregistered the webhook with the `diagral.unregister_webhook` action |

Use it in an automation to be warned when the state is not `connected`.

## Last webhook - Details

The time of the last Diagral event received, whatever its type. Disabled by default: enable it in the entity settings. A Diagral system that is rarely armed or disarmed sends few events, so a long silence is not an error by itself.

## Central connection - Details

Connected while the last refresh from the Diagral cloud succeeded. When Diagral does not answer, after the retries described above, the other entities become unavailable while this one switches to disconnected. Use it in an automation to be warned of a Diagral outage.
